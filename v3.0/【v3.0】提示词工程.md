# 【v3.0】提示词工程

## 1. 设计目标

FinSafe-QA V3.0 的提示词工程重点不再是单轮意图识别或图表生成，而是围绕新增的两个 Agent 能力展开：

1. **上下文管理**：判断用户当前问题是否依赖历史对话，并决定是否继承公司、指标、报告期等槽位。
2. **多意图自主规划**：将复杂问题拆解为查询、计算、证据/边界、分析、可视化等子任务，并生成可执行的依赖关系。

本版本的提示词工程文档采用“旧版 → 问题 → 新版 → 改动效果”的方式记录，因为 V3.0 是一次明显由评测反馈驱动的迭代。

---

## 2. 旧版提示词策略

V2.0 的提示词策略主要围绕“分析意图识别 + 结果解释 + 图表校验”设计。

### 2.1 旧版分析意图 Prompt

```text
你是 FinSafe-QA V2.0 的金融数据分析意图识别助手。

你的任务不是直接回答问题，也不是生成 SQL，而是把用户问题解析为结构化 JSON，用于后续可信 SQL、分析计算和图表生成。

支持的分析类型：
- single_metric：单公司单指标查询
- trend：单公司或多公司多期趋势
- top_n：某指标 TopN 排名
- compare：多公司同指标对比
- ratio_analysis：占比或效率计算
- growth_analysis：同比/环比增长率
- anomaly_detection：波动最大或异常识别
- driver_analysis：基于结构化数据的有限归因
- unsupported：超出当前结构化数据范围

输出字段：
analysis_type, companies, metrics, period, periods, top_n, chart_type, confidence, limitations
```

### 2.2 旧版分析结论 Prompt

```text
你是 FinSafe-QA V2.0 的分析结论助手。

你必须基于系统提供的结果表、计算字段和图表配置回答，不允许编造数据库中不存在的数值。

回答规则：
1. 先给结论，再给数据依据。
2. 每个关键判断必须绑定公司、报告期、指标、数值或变化率。
3. 明确区分“事实”和“推测”。
4. 不提供投资建议。
5. 当数据缺失、口径不一致或样本过少时，必须提示限制。
```

### 2.3 旧版图表校验 Prompt

```text
你是 FinSafe-QA V2.0 的可视化校验助手。

请基于分析意图、结果表字段和图表配置，判断图表是否适合当前问题。

校验重点：
- 趋势问题是否使用时间轴
- 排名和对比问题是否使用柱状图或横向柱状图
- 单位是否完整
- 图表维度是否与结果表字段匹配
- 2025Q3 与年度数据混合比较时是否提示周期口径差异
```

## 3. 旧版问题

旧版 Prompt 对 V2.0 的单轮分析和图表输出是够用的，但面对 V3.0 测试集暴露出三个问题。

| 问题 | 表现 | 影响 |
| --- | --- | --- |
| 缺上下文管理 | “那净利润呢”“和它比呢”“这些公司继续看研发费用”无法稳定继承上一轮槽位 | 多轮追问体验断裂 |
| 缺显式任务规划 | 复杂问题只输出一个 analysis_type，无法展示 query、calculation、analysis、chart 的执行顺序 | Agent 链路不可解释 |
| 复杂任务漏前置步骤 | 归因问题可能直接进入 analysis，没有显式规划先查结构化数据 | 违反“先查数再分析”的可信原则 |

第一轮 V3.0 模块评测也验证了这些问题：

| 指标 | 第一轮结果 |
| --- | ---: |
| 总用例 | 79 |
| 通过 | 41 |
| 通过率 | 51.9% |

主要失败集中在：

- 归因题缺少 `query` 前置任务。
- “差异、比较、筛选、找出”等表达没有触发 `calculation`。
- 带 ①②③ 的完整复杂问题被误判为追问，出现过度继承。

---

## 4. 新版提示词策略

V3.0 新增两类 Prompt / 策略层：

1. 上下文管理 Prompt
2. 自主规划 Prompt

当前工程默认用规则层稳定实现，但这些规则与 Prompt 设计保持同构，后续可以直接迁移到 LLM JSON 输出。

---

## 5. 新版上下文管理 Prompt

### 5.1 Prompt 内容

```text
你是 FinSafe-QA V3.0 的上下文管理模块。

你的任务不是回答问题，也不是生成 SQL，而是判断当前用户问题是否依赖最近对话，并输出可供下游执行的问题重写结果。

【输入】
- current_question：当前用户问题
- recent_history：最近 3 轮对话状态
  - companies：上一轮公司
  - metric_label：上一轮指标
  - period：上一轮报告期
  - analysis_type：上一轮分析类型
  - question：上一轮问题

【追问识别规则】
如果当前问题包含以下表达，且不是一个完整复杂问题，则优先判断为追问：
- “那…呢”
- “…呢？”
- “继续”
- “再看”
- “和…比”
- “为什么”
- “画图”
- “这些公司”
- “它们”
- “上述”

【槽位继承规则】
1. 当前问题缺公司，但上一轮有公司，则继承上一轮公司。
2. 当前问题缺指标，但上一轮有指标，则继承上一轮指标。
3. 当前问题缺报告期，但上一轮有报告期，则继承上一轮报告期。
4. 当前问题包含完整的新公司、新指标、新时间时，不继承旧上下文。

【防过度继承规则】
如果当前问题包含 ①②③ 等多步骤结构，应视为完整复杂问题，不因“这些公司”“它们”自动继承上一轮上下文。

【输出 JSON】
{
  "session_id": "当前会话 ID",
  "is_follow_up": true,
  "follow_up_reason": "追问触发槽位继承 / 新问题或无可继承上下文",
  "inherited_slots": {
    "companies": ["继承公司"],
    "metric": "继承指标",
    "period": "继承报告期"
  },
  "rewritten_question": "补全槽位后的完整问题",
  "history_size": 2
}
```

### 5.2 设计说明

| 设计点 | 作用 |
| --- | --- |
| 最近 3 轮窗口 | 避免无限历史导致过度继承 |
| inherited_slots 显式输出 | 让用户和评测脚本知道继承了什么 |
| rewritten_question | 下游不再处理省略句，降低任务规划难度 |
| 防过度继承规则 | 避免复杂问题中“这些公司”被误判为追问 |

## 6. 新版自主规划 Prompt

### 6.1 Prompt 内容

```text
你是 FinSafe-QA V3.0 的多意图自主规划模块。

你的任务不是回答问题，而是将用户问题拆解为可执行子任务，并为每个子任务分配类型和依赖关系。

【输入】
- rewritten_question：经上下文补全后的问题
- analysis_plan：已有单轮分析计划
- schema：当前可查询的结构化字段
- data_boundary：当前缺失字段、缺失公司和外部证据范围

【任务类型】
- query：结构化财务数据查询
- calculation：占比、增长率、效率、排名、筛选、差异、评分等规则计算
- evidence_or_boundary：研报、政策、业务量、TIDES、境外收入、固定资产、合同负债、销售费用等当前库外信息或证据任务
- analysis：基于查询、计算和证据生成结论
- visualization：生成图表配置

【拆解规则】
1. 如果问题包含 ①②③，按编号拆分子任务。
2. 如果问题包含多个问句或分号，按语义拆分。
3. 如果只有一个问题，但 analysis_type 较复杂，也要补出 query、calculation、analysis 等隐含任务。

【依赖规则】
1. query 必须优先执行。
2. calculation 依赖 query。
3. evidence_or_boundary 可与 calculation 并行，但必须基于问题边界识别。
4. analysis 依赖 query、calculation、evidence_or_boundary。
5. visualization 依赖 query 和 calculation，不允许先画图再查数。

【自动补任务规则】
1. 如果计划中没有 query，自动补充 query。
2. 如果问题包含“计算、占比、增长率、效率、评分、ROE、净利润率、周转、同比、环比、差异、比较、对比、筛选、找出”，必须包含 calculation。
3. 如果问题包含“研报、政策、TIDES、境外收入、业务量、在手订单、客户集中度、公允价值、投资收益、销售费用、合同负债、固定资产、雇员人数、流动比率、营业外收入、信用减值”，必须包含 evidence_or_boundary。
4. 如果问题包含“分析、解释、原因、驱动、风险、关系、影响”，必须包含 analysis。
5. 如果问题包含“画、图、折线图、双轴图、可视化”，必须包含 visualization。

【输出 JSON】
{
  "planner": "rules_autonomous_planner",
  "question_decomposition": [
    "子问题1",
    "子问题2"
  ],
  "tasks": [
    {
      "id": "task_1",
      "type": "query",
      "goal": "查询结构化财务数据",
      "depends_on": [],
      "status": "planned"
    },
    {
      "id": "task_2",
      "type": "calculation",
      "goal": "计算指标差异",
      "depends_on": ["task_1"],
      "status": "planned"
    }
  ],
  "execution_batches": [
    ["task_1"],
    ["task_2"]
  ],
  "context_used": false,
  "planning_notes": [
    "先查结构化数据，再做计算和分析。",
    "涉及研报、政策、业务细分或未入库字段时进入边界/证据任务。",
    "图表任务依赖查询和计算结果，不单独生成。"
  ]
}
```

### 6.2 设计说明

| 设计点 | 作用 |
| --- | --- |
| 任务类型固定枚举 | 让评测脚本可以自动判断任务覆盖情况 |
| depends_on 显式输出 | 让执行顺序可解释、可检查 |
| execution_batches | 支持展示哪些任务可并行、哪些必须串行 |
| evidence_or_boundary | 把“当前不能完整回答”变成一个可规划任务，而不是失败 |
| 自动补任务规则 | 避免归因题跳过查数、图表题跳过计算 |

## 7. 改动对比

| 模块 | 旧版 | 新版 | 改动作用 |
| --- | --- | --- | --- |
| 上下文管理 | 无独立模块，只处理单轮问题 | 新增 session、history、inherited_slots、rewritten_question | 支持多轮追问和槽位继承 |
| 复杂问题拆解 | 单个 analysis_type | question_decomposition + tasks | 让复杂问题可拆、可评测 |
| 任务类型 | 分析意图类型 | query / calculation / evidence_or_boundary / analysis / visualization | 更接近 Agent 执行链路 |
| 执行顺序 | 隐含在代码中 | depends_on + execution_batches | 让任务依赖透明可审计 |
| 外部证据边界 | limitations | evidence_or_boundary 任务 | 把“不能回答完整”纳入规划，而不是静态提示 |
| 归因问题 | 可能直接 analysis | 自动补 query + evidence_or_boundary | 保证先查数再分析 |
| 计算识别 | 主要识别“计算/占比/增长率” | 增加“差异/比较/对比/筛选/找出” | 覆盖更多真实投研表达 |
| 追问判断 | 无系统化规则 | 增加追问模式和防过度继承 | 减少断上下文与误继承 |

## 9. 当前实现说明

当前 V3.0 工程中，提示词策略主要落在两个地方：

| 文件 | 作用 |
| --- | --- |
| `src/prompts.py` | 保留 LLM 版本的意图识别、分析结论、图表校验 Prompt |
| `src/engine.py` | 用规则层稳定实现上下文管理与自主规划，保证本地评测可复现 |

为什么当前默认规则层？

- 规则层更稳定，便于本地离线评测和自动化回归。
- Prompt 结构已经与规则层同构，后续可替换为 LLM JSON 输出。

## 10. 总结

V3.0 的提示词工程从“让模型理解一个问题”升级为“让系统规划一个任务”。

这次迭代的核心价值是：

- 让多轮追问可被记录、继承和复现。
- 让复杂问题从黑盒回答变成显式任务链。
- 让缺失外部证据的问题进入边界任务，而不是编造结论。
- 让评测能直接检查 Agent 的中间过程，而不只看最终回答。

V3.0 相比 V2.0 的核心变化是：不追求一次性回答更多，而是让复杂能力变得可控、可解释、可评测。
